## 二之二、调用外部模型的部分（需特别说明）

用户侧写的「AI 解读」会**调用外部大模型接口**，本组在此明确披露：

| 项目 | 说明 |
|---|---|
| 服务提供方 | DeepSeek（`https://api.deepseek.com`），OpenAI 兼容接口 |
| 触发方式 | **用户点击「用 AI 解读」才发送**，不点不发送 |
| 发送内容 | 仅统计结果：总播放次数、Top 歌手与歌曲、24 小时分布、夜间占比等。**不含 Cookie、手机号、账号 ID 或任何原始接口响应** |
| 凭据位置 | `DEEPSEEK_API_KEY` 只保存在服务端 `.env`，**不进入前端页面**，也不写入日志 |
| 降级策略 | 未配置 Key 时端点返回 `disabled`，前端自动回退到本地规则文案。**评委无需任何第三方凭据即可完整跑通项目** |
| 数字可靠性 | 所有数字由本地统计引擎计算，提示词明确要求模型「只能使用给定数据中出现过的数字，不得编造」。实测 1.7s 返回，文中数字逐条核对无误 |
| 已知不足 | 模型曾把两个不等的数值表述为「并列」（数字正确、比较措辞不严谨），说明仍需人工复核输出 |

## 四、AI 使用中的问题与人工纠正（可作为答辩素材）

AI 生成的代码并非一次可用，本组在验收中发现并修正了以下问题：

| # | 问题 | 后果 | 发现方式 |
|---|---|---|---|
| 1 | 前端误用 Python 语法 `'、'.join(bits)` | JS `TypeError`，侧写页整块崩溃 | 本地跑分析引擎时暴露 |
| 2 | 「本周新歌」统计口径错误：拿两个各取前 100 名的榜单互相比对 | 得出「100% 都是新歌」的错误结论 | 核对真实数据时发现逻辑不成立 |
| 3 | 侧写首版输出 6 大块数据，信息过载 | 用户明确反馈「太多看着累」 | 用户验收 |
| 4 | 「1 年 / 1 月」筛选无法实现：接口不提供任意时间段历史 | 若不核实就会伪造数字 | 实测 `get_recent_plays` 仅回溯约 2 天 |
| 5 | 测试断言写错（`artistAll` 只统计历史榜，断言按两榜相加） | 误判为代码缺陷 | 人工核对数据口径 |
| 6 | AI 解读首版把模型返回的两个不等数值说成「并列」 | 结论表述不准确（数字本身无误） | 本组逐条核对模型输出与本地统计值 |
| 7 | 本地测试脚本漏了 `JSON.parse` 这一步 | 一度误判前端解析有 bug，实为测试脚本自身问题 | 对照 `callTool` 源码确认前端正确 |

> 结论：AI 用于**提效**（前端实现、文档整理），但**需求判断、口径核实、结果验收由本组负责**。
